# LABJUDGE-EXT09 三草案判定

## 总览

三草案构成一套**分层治理接口**:①定“谁有权重做/如何见证”,②定“缓存锚在什么条件下可判 DONE / BLOCKED”,③定“A1 堆叠升级时各层权责与停让”。三者耦合点在**②的 DONE/BLOCKED 边界**与**③的 L0 确权锁**——若边界模糊,①的“探针/证书”区分会被制度性绕过。

---

## ① CIRC 重做立项

**路线选择:稳健(有条件)。**
- 以“主线 B 见证证书化内嵌 A”为主轴,把 A 降为 C(探针),符合**权责分离**原则:重做立项的合法性来自 B 的见证,而非 A 的自证。
- AC1–AC5 作为验收锚点是合理的,但**“AC”未在本草案给出可判定谓词**——若 AC 是“能力项”而非“布尔可机检项”,则机器复核只能做**形式校验**,实质判定仍需人。

**验收判据可否机器复核:部分。**
- 可复核:证书存在性、签名链、探针调用次数、内嵌 A 的引用完整性。
- 不可复核(需补):AC 的“语义达成度”——例如“探针仅探针”若定义为“不得写入主状态”,需给出**状态写权限矩阵**才能机检。

**制度漏洞:**
- **探针越权风险**:C 仅探针,但若探针可触发 B 的写路径,则“仅探针”名存实亡。需在 AC 中显式禁止 **probe→commit 直通**。
- **证书自签闭环**:若 B 的见证证书由 B 自身签发,A 内嵌后形成自证。需外部锚(时间戳/第三方/不可篡改日志)。

**对本票:不反对,但附条件——AC 必须至少 3 条为布尔可机检,且探针写权限须显式封死。**

---

## ② 缓存锚域限条款

**路线选择:方向正确,但边界定义偏“列举式”,稳健性不足。**
- “fallthrough DONE 四条件”+“BLOCKED 四触发”+“缓存锚≠内容认证”——三句话把**状态判定**与**语义认证**解耦,这是对的。
- 问题在于:**四条件/四触发是并列穷举还是权重组合?** 若是穷举,漏一条即误判;若是组合,需给出**优先级与冲突消解**。

**验收判据可否机器复核:大部分可,但有灰区。**
- DONE 四条件若均为**可观测事件**(如:fallthrough 路径命中、锚域匹配、无 BLOCKED 触发、缓存版本一致),则可机检。
- BLOCKED 四触发若含**“疑似”“不一致”**等模糊词,则不可机检,必须量化为阈值或布尔。

**制度漏洞(重点):**
1. **DONE/BLOCKED 边界竞态**:同一事件可能同时满足 DONE 条件与 BLOCKED 触发(如:fallthrough 命中但锚域跨域)。草案未给**冲突时默认保守(BLOCKED 优先)** 的规则——这是最危险的漏洞。
2. **“缓存锚≠内容认证”被反向利用**:既然锚不等于认证,那么 DONE 可能被解读为“锚域内可用”而非“内容可信”。需显式声明:**DONE 仅表状态可推进,不表内容已认证**;否则下游会把 DONE 当认证用。
3. **BLOCKED 逃逸**:四触发若可被“重试/降级/旁路”绕过,则 BLOCKED 不具阻断力。需规定 BLOCKED 期间**禁止 fallthrough 写主状态**。

**对本票:反对“当前形态”通过。** 理由:未定义 DONE/BLOCKED 冲突优先级,且未封死“DONE 被当认证用”的语义滑坡。建议补:**BLOCKED 优先于 DONE** + **DONE 不传递认证语义** 两条硬规则后再判。

## ③ A1 堆叠升级

**路线选择:合理,但“停层”规则是双刃剑。**
- L0 确权锁边界、L1/L2 契约 JSON 化、DISPUTED 停层——三层结构清晰,JSON 化利于机检。
- **DISPUTED 停层**是安全阀,但若停层条件过宽,会导致**系统性僵死**;过窄则形同虚设。

**验收判据可否机器复核:较高。**
- L0 锁边界:可机检(权限矩阵、锁粒度、释放条件)。
- L1/L2 契约 JSON:可机检(schema 校验、字段完整性、版本兼容)。
- DISPUTED 停层:取决于**触发条件是否布尔化**。若为“存在争议”则不可机检;若为“L1/L2 契约校验失败”或“L0 锁冲突”,则可机检。

**制度漏洞(重点):**
1. **层级停让规则缺失**:草案说“DISPUTED 停层”,但未说**停在哪一层、由谁解停、超时如何**。若 L1 争议却停 L2,则 L1 可能继续污染;若停 L0,则全局僵死。
2. **L0 确权锁的“锁边界”未定义释放**:锁若不可重入、不可超时释放,则单点故障即全栈停摆。
3. **JSON 契约的版本漂移**:L1/L2 契约 JSON 化后,若 schema 演进无**向后兼容规则**,旧层会被新契约误判为 DISPUTED。

**对本票:不反对,但附条件——必须补“停层归属层 + 解停主体 + 超时升级”三要素,且 L0 锁须有超时/看门狗。**

## 跨案耦合风险

- ①的“探针”若走 ②的 fallthrough 路径,可能绕过 ③的 L0 确权锁 → **探针成为锁旁路**。
- ②的 DONE 若被 ③的 L1/L2 契约当作“认证输入”,则违反“缓存锚≠内容认证” → **语义污染跨层传播**。
- ③的 DISPUTED 停层若停在 L1,而 ②的 BLOCKED 在 L2 触发,则 **状态机可能死锁**(L1 等 L2 解停,L2 等 L1 解停)。
